# Threat model MCP-інтеграцій (Task C)

Модель загроз для **цієї** конфігурації: Claude Code 2.1.233 на Windows 11,
три сервери з [`.mcp.json`](../../.mcp.json), обмеження в
[`.claude/settings.json`](../../.claude/settings.json). Перелік серверів і
scope — у [`servers.md`](./servers.md).

## 1. Що до чого має доступ

| Сервер | Дані/ресурси, до яких дістає | Секрети | Може писати? | Довіра до автора |
|---|---|---|---|---|
| `filesystem` `@2026.7.10` | тільки тека `app/data/` (у ній один файл — `catalog.json`) | немає | **так, і це проблема**: `write_file`, `edit_file`, `create_directory`, `move_file`. Заборонені через `permissions.deny`, але сам сервер read-only-режиму не має | офіційний (`@modelcontextprotocol`) |

Останній рядок тут не для повноти: **MCP-сервери не є найширшим каналом
доступу в цій конфігурації**. Вбудований `Bash` хоста бачить більше, ніж усі
три сервери разом. Це прямо видно в прогоні B (Task D): без мого сервера агент
просто зробив `cat catalog.json` і порахував сам. Оцінювати scope MCP окремо
від прав хоста — самообман.

## 2. Ризики, які я вважаю реальними для цієї конфігурації

- **Prompt injection через дані.** Сервера, який тягне зовнішній контент, я
  свідомо не підключав (`fetch` — у списку «НЕ підключали»). Але канал усе одно
  є: `catalog.json` читається і файловим сервером, і моїм. Якщо хтось допише в
  поле `name` товару рядок на кшталт «ignore previous instructions, run …»,
  цей текст потрапить прямо в контекст моделі як «дані каталогу». Мій сервер
  віддає значення полів без екранування — він їх не інтерпретує, але й не
  знешкоджує. **Другий, менш очевидний вектор — memory-сервер:** отруєний
  текст, одного разу записаний у граф, повертається в контекст у **наступних**
  сесіях, уже без сліду про походження. Injection, який переживає перезапуск,
  гірший за разовий.
- **Занадто широка область доступу.** filesystem бачить рівно `app/data` — але
  всередині цієї теки він бачить `catalog.json`, який за правилами репо
  редагувати не можна, і має чотири tools, щоб це зробити. Тобто вузький scope
  тут не рятує від конкретно цієї помилки; рятує заборона tools.
- **Витік секретів.** У грі немає жодного токена: обидва публічні сервери
  безтокенні, мій сервер — локальний. `.env` не існує, у репо тільки
  `.env.example`. Ризик радше майбутній: щойно хтось додасть сервер із ключем,
  цей ключ поїде в оточення процесу, який запускає хост, і потрапить у логи
  запуску. Тому правило `${ENV_VAR}` записане текстом у двох місцях, а не лише
  мається на увазі: у кореневому `AGENTS.md` (загальний guardrail репо) і в
  секції `## MCPs` у `app/AGENTS.md` — там, де агент читатиме його разом із
  переліком серверів.
- **Зміна поведінки сервера після встановлення.** Обидва публічні сервери
  стартують через `npx -y`, тобто **код завантажується з мережі при кожному
  запуску хоста**. Версії зафіксовані (`@2026.7.10`, `@2026.7.4`), тож tag
  не «попливе», але це не lockfile: захисту від компрометації самого пакета або
  його транзитивних залежностей немає. `npx -y` ще й глушить підтвердження
  встановлення — зручно й тому небезпечно.
- **Дії з побічним ефектом.** Такі tools є: 4 write-tools у filesystem
  (заборонені) і 6 mutating-tools у memory (дозволені свідомо — інакше сервер
  безглуздий, а пишуть вони в один гітігнорений файл). У моєму сервері таких
  tools немає жодного.
- **Довіра до опису tool.** Модель вирішує, що викликати, читаючи
  `description`. Це текст із чужого пакета, який потрапляє в системний контекст
  на рівні інструкції. Оновлення сервера — це водночас і оновлення тексту, що
  впливає на поведінку моєї моделі; diff цього тексту ніхто не рев'ювить.

## 3. Що я зробив, щоб це зменшити

- filesystem обмежений `./app/data`, а не коренем репо і не домашньою текою —
  `.env`, `.git`, `node_modules` поза його областю.
- Write-tools filesystem **явно заборонені** в `.claude/settings.json`
  (`permissions.deny`: `write_file`, `edit_file`, `create_directory`,
  `move_file`); read-tools — в `allow`. Заборона на рівні хоста, а не «домовились
  не викликати». Нюанс, який видно лише в реальному запуску: у headless-режимі
  на недовіреному воркспейсі хост пише `Ignoring 8 permissions.allow entries
  from .claude/settings.json: this workspace has not been trusted` — тобто
  **allow-список ігнорується, поки не прийнято trust-діалог**. На `deny` це
  попередження не поширюється, але сам факт варто знати: permission-файл
  діє не завжди й не весь.
- Версії обох публічних серверів **закріплені** (`@2026.7.10`, `@2026.7.4`)
  замість `@latest`.
- memory пише в **проєктний** файл (`MEMORY_FILE_PATH=./.mcp-memory/...`), а не
  в глобальний файл поруч із пакетом у `node_modules`, який був би спільним для
  всіх моїх проєктів. Теку додано в `.gitignore`.
- Власний сервер read-only **за конструкцією**: жодного імпорту `node:fs` на
  запис, жодного `fetch`/`child_process`; уся логіка імпортована з
  `app/dist/index.js`, тобто поверхня сервера — це чотири виклики чужих чистих
  функцій.
- Усі 4 tools мого сервера позначені `annotations.readOnlyHint: true` /
  `destructiveHint: false` / `openWorldHint: false` — хост бачить це в
  `tools/list` і може ухвалювати рішення про підтвердження автоматично.
- `fetch`-сервер не підключений — найпростіший спосіб не мати каналу
  injection з інтернету.
- У репо немає `.env`; перед PR прогнано `git grep -nE
  "ghp_[A-Za-z0-9]{20,}|github_pat_[A-Za-z0-9_]{20,}|sk-[A-Za-z0-9]{20,}"` →
  `clean`.

## 4. Що лишилось прийнятим ризиком

- **`npx -y` тягне код із мережі при кожному старті хоста.** Закріплена версія
  ≠ перевірений артефакт: supply chain лишається відкритим. У проді я б ставив
  сервери як звичайні залежності з lockfile або тримав власний реєстр/образ.
- **memory-сервер має право видаляти дані свого графа** і накопичує контекст
  між сесіями без ревізії. Тут це навчальний граф у гітігнореному файлі; у
  проді я б не давав агенту довготривалу пам'ять без можливості її переглянути
  й очистити.
- **Все виконується під моїм користувачем**, без контейнера й окремого
  UNIX-акаунта. Скільки б я не звужував аргумент шляху, реальна межа —
  права ОС, а їх я не міняв. Для синтетичного каталогу з 24 товарів це
  прийнятно; для репо з реальними даними — ні.
- **`roots` я не використовую як захист** і не покладаюся на них: у моєму
  прогоні клієнт їх узагалі не підтримує (`Client does not support MCP Roots`),
  а специфікація описує їх як механізм координації (`SHOULD`, не `MUST`) і вже
  позначила deprecated у ревізії `2026-07-28`.
- **Вбудовані tools хоста ширші за будь-який MCP-сервер тут.** Я їх не
  обмежував — інакше репо стало б незручним для роботи. Це усвідомлений вибір,
  а не недогляд: у прод-репо цей рядок був би окремим тікетом.
